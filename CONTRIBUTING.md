# Contributing to SSTRE

This guide applies to all five SSTRE repositories. Component repositories link here
instead of duplicating it; they may add repository-specific notes in their own
`CONTRIBUTING.md`.

> **Status: Phase 0 (bootstrap and research).** There is no playable build, no
> released tooling and no stable interface yet. Conventions below are proposals
> that the owner may still change; items marked **Owner decision pending** are
> not in force.

## Ground rules

1. **No game data.** Never commit, attach or upload original Serious Sam files
   (`.gro` archives, textures, models, worlds, sounds, music), extracted assets,
   AI-generated derivatives of them, or screenshots/renders that show them. This
   applies to commits, issues, pull requests, discussions and release assets.
   Users supply their own legally acquired copy and all processing happens
   locally. Git LFS is not a loophole. CI never needs game data. See
   [`.gitignore`](./.gitignore) and the forbidden-file check in
   [`scripts/validate_repo.py`](./scripts/validate_repo.py).
   *Exception:* SSTRE-Engine will preserve upstream engine history, which
   already contains a small number of upstream-distributed `.gro`/`.tex`
   files. Their status is part of the licensing audit; do not add more.
2. **No model weights or secrets.** No checkpoints (`.safetensors`, `.ckpt`,
   `.pth`, `.onnx`, ...), API keys, tokens or `.env` files. Reference models by
   name, source URL and content hash in manifests instead.
3. **AI-generated assets and code.**
   - AI-generated or AI-upscaled images derived from game assets fall under
     rule 1: they are never committed.
   - Synthetic test fixtures generated by AI must be marked as such in the PR
     description, together with the tool/model used and its license terms.
   - AI-assisted code or documentation is allowed. The human contributor is
     responsible for it, must have reviewed it, and must be able to certify the
     sign-off below. Mention substantial AI assistance in the PR description.
   - Release builds must not require a live LLM or external AI API (plan §3).
4. **Separation of repositories.** Respect the dependency direction in
   [`docs/architecture/cross-repo-contracts.md`](./docs/architecture/cross-repo-contracts.md):
   Remaster-Toolkit contains no Serious Sam-specific code; SSTRE-Manifests is
   declarative data; SSTRE-Engine does not depend on Python or inference
   services.
5. **Upstream code keeps its license.** Do not relicense, strip or rewrite
   copyright headers or notices in upstream engine code.
6. **Be honest about status.** Do not document planned features as implemented,
   add badges for checks that do not exist, or claim compatibility that was not
   tested.

## Commits

- **Conventional Commits** (proposed): `type(scope): summary`, e.g.
  `docs(adr): add ADR-005 engine foundation`, `ci: pin setup-python by SHA`.
  Types: `feat`, `fix`, `docs`, `ci`, `build`, `test`, `refactor`, `chore`.
  Mark breaking contract changes with `!` and a `BREAKING CHANGE:` footer.
- **Sign-off: Developer Certificate of Origin (DCO)** — adopted by the owner on 2026-11-27; no CLA. Every commit must carry a `Signed-off-by: Name <email>` trailer (`git commit -s`), certifying the [DCO 1.1](https://developercertificate.org/). Contributors keep their copyright; contributions are accepted under the license of the repository (or, in SSTRE-Manifests, of the directory) they are made to.
- **DCO check (proposal, not yet required).** [`.github/workflows/dco-proposal.yml`](./.github/workflows/dco-proposal.yml) verifies that every non-merge commit in `base..HEAD` has a `Signed-off-by:` trailer matching the author's e-mail. It runs only on manual dispatch and is not a required status check, because the existing commits are not yet signed off (owner decision pending on how to handle them). Once that is settled it can be enabled for pull requests and made required.
- Keep commits focused; do not mix formatting churn with functional changes.

## Branches and pull requests

- Default branch: `main`. Never force-push to `main` or rewrite shared history.
- Branch names: `<type>/<short-topic>`, e.g. `docs/rd-002-hd-assets`,
  `feat/gro-reader`, `fix/link-check`. Phase work may use `phase<N>/<topic>`
  (for example `phase0/bootstrap`).
- Open a pull request; fill in the template; keep the change reviewable.
- Changes that touch a cross-repo contract (anything in `schemas/` or a CLI
  interface) need a linked ADR or an issue in the umbrella repository and, if
  they affect several repositories, coordinated PRs that reference each other.

## Architecture decisions (ADRs)

Decisions are recorded separately from research:

- Research dossiers live in the umbrella `docs/research/` (`RD-NNN-topic.md`).
- ADRs live in the umbrella `docs/adr/` (`NNNN-title.md`, from the template
  `docs/adr/0000-template.md`) with context, decision, alternatives,
  consequences and status (`proposed`, `accepted`, `superseded`, `rejected`).
- An unresolved technical choice stays `proposed`. Accepting or superseding an
  ADR requires owner approval in the PR.

## Local checks

From the umbrella repository root (Python 3.10+):

```sh
python -m venv .venv
# Windows: .venv\Scripts\activate    POSIX: . .venv/bin/activate
python -m pip install "jsonschema==4.26.0"
python scripts/validate_repo.py
```

The same script runs in CI (`.github/workflows/docs-and-schemas.yml`). It checks
JSON Schemas against draft 2020-12 including their synthetic `examples`,
relative Markdown links, and forbidden game-data/model-weight files. Pass
`--root <path>` to run it against a sibling repository checkout.

## Reporting

- Bugs, research questions and asset-mapping problems: use the issue templates
  in the relevant repository (the umbrella if unsure).
- Security vulnerabilities: see [SECURITY.md](./SECURITY.md); do not open a
  public issue.
