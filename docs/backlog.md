## Estimation assumptions

- One person-day (pd) = ~6 focused hours by a contributor already familiar with C++/CMake and Python.
- Reference PC with a ray-tracing-capable GPU is available; user-owned Steam Classic + HD installs available locally (Phase 0 lead inspection). GOG editions are **not** available — anything GOG-specific is out of these estimates.
- Ranges cover "works roughly as documented" (low) to "requires patching build files or reverse-engineering" (high). They exclude review/approval wait time. They are not commitments; re-estimate after POC-01/02.
- No game data in CI; local-only steps produce aggregate reports (numbers + hashes) only.

#### Rules for stage M0.1 packages

1. **Root cause before fixes.** Each fix package starts from a confirmed root cause recorded in the defect register (field "confirmed root cause") and in the owning EXP report.
2. **Universal solutions first.** Prefer engine-level, RTGL1-level and asset-pipeline solutions. No per-texture, per-entity or per-level workaround; no classification by texture colour or filename. An unavoidable exception is declarative data with a documented reason (proposed ADR-0016). Generic RTGL1 improvements are preferred where they fit, so that they can go upstream (technical content only, no asset references).
3. **No silent quality change.** New behaviour sits behind an explicit cvar or profile setting; a default changes only when the comparison shows it is better, and the change is stated in the EXP report and release notes (M1 rule 1 applies).
4. **Low cost first.** No explosion of generated point lights, no extra RT bounces without measurements, cached static data, configurable volumetrics, no unnecessary particle geometry expansion, no excessive texture memory. Each substantial correction gets a short on/off A/B FPS measurement under the lock; the formal regression run is POC-91 (E3, quiet mode). Performance opportunities are recorded for RD-014 and M1, not implemented now unless they are correctness fixes.
5. **All renderers, both games.** TFE and TSE; RT, Vulkan and OpenGL; validation is not limited to the three showcase levels, and non-showcase levels get no new manual lights or level-specific renderer exceptions.
6. **Publication gates.** Screenshots and per-asset data stay local; public reports name levels, entity classes and blend/flag names only (GATE-05). The preview2 build stays unchanged as the reference.

### Rules for all stage M1–M5 packages

1. **No silent quality reductions.** A change that alters the image beyond the quality-guard threshold (POC-45) ships only as an explicit, documented graphical setting with measured cost and benefit. Defaults change only with owner approval.
2. **Profile first.** An optimization package starts only when a profile (POC-36) attributes a measurable share of frame time to its area.
3. **Frame generation never counts.** Results are reported per render mode: **N** native, **S** spatial upscaling (FSR 1.0), **T** temporal upscaling, **FG** frame generation. FG results are reported separately and never toward the target.
4. **Diminishing-returns stop rule.** Stop stage-M1 optimization and escalate to the owner when (a) two consecutive optimization packages each gain less than max(3 % mean FPS, the measured regression threshold) on the scene set, or (b) the stage budget (proposed 25 pd, owner to confirm) is spent, while the target is still missed. The escalation memo (POC-46) lists the architectural limits found, the remaining gap per scene and mode, and realistic alternatives.
5. **Every graphical feature in M3/M2 (in that order, [issue #22](https://github.com/Handelsonderneming-S-D-Broekhoven/SSTRE/issues/22)) is benchmarked alone and combined** against the optimized M1 baseline (POC-53). A feature with disproportionate cost is optimized, applied selectively or replaced before it may be on by default.
6. TFE and TSE both. Vulkan and OpenGL raster keep working (regression run in every package that touches the engine).
